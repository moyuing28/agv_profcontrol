# SampleProject 项目说明

本文介绍当前项目的功能、配置、运行流程和限制，供维护者和 AI 理解源码。修改功能后同步更新本文；变更记录放在 Git 提交中。实际行为以源码及现场验证为准，不要把规划功能当作已实现功能。

## 项目用途与运行环境

这是 ProfControl 中运行的 C# 脚本项目，入口类为 `ProfControl.SampleProject : IAppScript`，通过 partial class 拆分文件。依赖宿主软件的地图、AGV、货物模型及 API，不是独立控制台程序。

目前支持空车移动、点到点清障搬运、多条源巷道到多条目标巷道的业务批次搬运，以及动态停车。业务批次调度由 `CargoBatchManager.cs` 实现。

## 地图和标识约定

- `车库位`：货物存放站点的总分类，用于库位筛选，不是 AGV 停车位；取放货区域由朝向子分类决定。
- `车库位朝右`、`车库位朝上`、`车库位朝左`、`车库位朝下`：四种朝向子分类，名称同时也是货物区域名称。每个车库位站点只配置其中一个朝向，并保留所属巷道分类和 `车库位` 总分类。
- `入口`：货物巷道和停车巷道的进出口确认点；每条识别出的巷道需要唯一入口。
- `agv停放点`：AGV 实际停车位，入口不作为停车位。
- `01`～`25`：货物巷道子分类名称，保持两位数字格式，在 `script.cs` 的 `巷道子分类名称` 中配置；当前巷道批次要求每个分类完整对应一条物理巷道。
- `BelongPocketLines` 表示站点所属巷道；`OrderStations` 是从内部到门口的拓扑顺序，不要按站点编号排序。
- 内部 `PocketKey` 使用巷道首站 Mark，不等于入口编号，也不等于子分类名称。
- `CreatePocketMoveBatch(new[] { "01" }, new[] { "03" })` 的参数是子分类名称，不能传内部 PocketKey 或入口站点号。
- 旧地图示例：02 巷道为 `4 → 38 → 36 → 7 → 67`，入口 67；03 巷道为 `3 → 18 → 22 → 23 → 25`，入口 25。该示例不代表新地图配置，不可把示例编号写死为通用规则。
- 入口到达被用于释放通行占用；地图布点必须保证在此确认时车辆已退出。途中 `API.On` 可为空，不能把空值当作已退出。

## 地图配置缓存

`Init()` 在初始化场景及启动调度之前调用 `LoadMapConfiguration()`。配置保存在当前 `SampleProject` 实例内，运行期间只读，不使用跨实例的静态全局变量。`SubCategoryCollection` 只在此加载流程读取；停车巷道仍由 `LoadParkingLanes()` 在启动时使用缓存分类构建并校验。

- 缓存分类的站点列表和编号集合、物理巷道的入口与深浅顺序、巷道分类名称到内部 Key 的对应关系、货位朝向区域。
- 启动时汇总缺失分类、入口不唯一、重复货位、巷道分类不完整、朝向缺失或重复等问题。无效巷道不用于批次创建、入口准备及卸货容量计算；朝向错误仍在取放货时保持等待。
- `CreatePocketMoveBatch()` 只接受 `巷道子分类名称` 中已加载且校验通过的名称。站点查询也只返回通过巷道校验的配置；`GetSelectableStations(true)` 返回所有有货货位，`GetSelectableStations(false)` 返回所有空货位。查询不检查外侧阻挡、巷道锁或任务预留，不等同于卸货准入。
- 货物有无、连续可达空位、AGV 可用性、锁、容量预留均实时计算。缓存中的站点对象用于读取当前货物状态，不缓存 `IsEmpty()` 结果。
- 本版本不支持运行期间修改地图或分类后自动生效，也不提供在线刷新。修改配置应在任务结束、确认现场状态后重新加载脚本；重新加载会执行现有测试货物及车辆初始化，不能作为无副作用的刷新操作。不要重复调用 `Init()` 刷新配置。

`mapConfigurationLoaded` 防止同一个脚本实例重复加载。调度周期为 1 秒，每轮按需读取货物及车辆当前状态，不会每秒重建地图配置。

## 三层任务与两类批次编号

1. `CargoMoveBatch`：客户的一次巷道搬运要求，记录创建时的源货物清单。
2. `CargoMoveItem`：每个源有货站点一条业务明细，等待时不创建执行任务，也不固定卸货位。
3. `TaskInfo`：已落实资源和车辆的执行任务。

业务关联用 `CargoBatchId`、`CargoItemId`、`TaskId`。清障步骤组用 `ClearanceBatchId`、`ClearanceSequence` 和 `PendingClearanceBatches`，不要混为一套批次。

清障搬运负责搬开阻挡货物，再搬目标货物，**不包含自动搬回原位**。步骤按队列激活，但前车退出取货巷道后即可激活后续步骤，不必等前车回家。

## 业务批次创建与派发

统一使用 `CreatePocketMoveBatch(IEnumerable<string> sourcePocketNames, IEnumerable<string> targetPocketNames)`，两个参数均传数组或列表，不提供双字符串重载；返回 `CargoBatchCreateResult`，检查 `Success`、`Error` 和成功后的 `Batch.BatchId`。

- 创建时校验巷道配置，按物理巷道去重并保留顺序；来源目标不能重叠。跳过空来源，全部无货则拒绝。
- 支持 `CreatePocketMoveBatch(new[] { "01", "02", "03" }, new[] { "06", "07" })`，两个集合长度不限；单巷道也统一传单元素数组或列表。
- 创建时汇总各目标可进入空位减去在途预留的容量，不足则整批拒绝。创建结果的 `RequiredCount` 和 `TargetCapacities` 返回待搬数量及容量明细。
- 创建时只建立货物清单并校验目标总容量，不提前给所有货物分配目标巷道。每件货准备派车时，才按目标列表顺序选择目标并预留一个容量名额；未找到车辆时不保留此次临时预留。
- 派车后固定目标巷道，不在途中切换。取货完成后，取得目标巷道通行锁时才确定具体卸货货位，选择可进入的最深空位。
- 例如来源 `[06,07,08,09,10]`、目标 `[01,02,03]`：先分配 01 的容量，再分配 02、03，不做平均分配。若 01 能放两件，前两件即使尚在运输途中也已占满预留名额，后续货物即可分配到 02，无需等待 01 实际卸完；若 01 足够容纳整批，就只使用 01。
- 多个来源和目标之间可并行推进，但同一巷道的进出受通行锁保护；容量预留决定还能分配多少件，通行锁决定车辆何时可以进入。
- 来源按巷道轮询，某来源被占用不阻塞其他来源；每条内部从外向内取货，仍受并行上限约束。
- 批次查询返回独立的来源、目标名称列表和查询时的目标容量快照。ScopeId 为名称逗号拼接，仅供展示；单值 TargetPocketKey 只在单目标时赋值，多目标调度使用 TargetPocketKeys。
- 当前只允许一个未完成业务批次；已有其他未完成执行任务或清障队列时拒绝创建。
- 创建按当时有货的来源站点建立搬运清单，不保存货物对象引用，也不比较货物身份，不马上派车；后来其他站点新增的货物不会自动加入原批次。
- 调度按源巷道外侧到内侧挑选等待明细，检查来源站点存在且有货、外侧货物是否搬离、源锁、并行名额、目标容量和可用车辆。批量任务进入取货巷道前及取货等待结束后仍检查来源站点有货，不做对象身份检查。
- 资源成立才关联 TaskInfo、占用取货巷道并派车；目标巷道此时可以被前车占用。
- 创建、调度和业务查询使用 `cargoBatchSync` 协调共享状态。
- 来源站点不存在或已无货、执行关联丢失或派车结果不确定时进入 `NeedsReview`，不擅自释放已占资源或重复派发。

## 搬运状态机

普通跨巷道搬运：

```text
None / 业务调度派车
→ GoParkingExit（车辆从停车巷道出发时）
→ GoPickEntrance → GoPick → Picking → Picked
→ GoPickExit → GoDropEntrance → GoDrop → Dropping → Dropped
→ GoDropExit → ExitedDrop → GoHome → Finished
```

- `Arrived` 同时检查 AGV 空闲和 `API.On == 目标Mark`，到入口后才发下一段指令，避免每秒采样漏掉快速经过的入口。
- `Picking` / `Dropping` 当前等待 `PickDropDelay = 5` 秒并通过 `MoveToOtherArea` 转移货物模型，不能等同于已接入真实抬升/卸货完成反馈。
- `GetStationCargoArea` 从初始化生成的站点朝向映射获取货物区域，四个名称配置在 `script.cs` 的 `GarageDirectionAreas` 中。取货从起点对应区域转入 AGV 的 `车` 区域，卸货从 `车` 区域转入终点对应区域；例如 `车库位朝右 → 车 → 车库位朝上`。
- 取放货时若站点不存在、不属于有效车库货位、未匹配朝向分类或匹配多个朝向分类，通过 `WaitReason` 输出原因，保持当前 `Picking` / `Dropping` 阶段，不执行本次转移，也不推进为完成。后续调度读取同一份配置缓存，修正分类后需重新加载脚本；不会自动回退使用 `车库位` 区域，也不另行校验宿主货物区域对象是否存在。
- `Picked` 时申请卸货通行锁并确定可进入的卸货位，成功才离开取货位。失败则原地等待，继续持有取货锁。
- 到取货出口释放取货锁，并在同轮下发去卸货入口的指令。后车此时可以取下一份货。
- 卸完仍保持卸货锁，直到到达卸货出口才释放。
- 同巷道内部搬运直接去卸货位，持续持有同一通行锁，卸完退出后释放。
- 空车移动走 `GoMove → Finished`，不同于货物搬运流程。
- 单纯移动（含进出入口、回停车位）只调用 `GoTo(mark)`，不设置 `staID` / `staAction`；取货、卸货才设置 `pick` / `drop` 动作。
- 派车不要求 AGV 位于停车位：停车区外空闲且没有未完成任务、未执行停车流程的车也可参与分配；停车区内另需满足可出库条件。
- 当前搬运车辆必须完成动态回家停车才成为 `Finished`；尚未实现卸完直接接下一单。

## 容量预留与通行锁

`DropCapacityReserved` 预留目标巷道容量，防止空位超分；`PocketLocks` 控制实际巷道通行，两者不可合并。

- 动态任务通过 `DropPocketKey` 确定目标巷道；取得卸货锁后才填写具体 `ToMark`。
- `DropSlots()` 从入口向内检查连续空位，排除被外侧货物挡住的内部空洞，再按深到浅选位。
- 固定目标任务仍保留指定货位，动态任务不能抢占或挡住固定预留货位。
- 卸货完成后解除容量预留，货位转为实际占用；卸货通行锁继续持有到出巷道。
- 释放锁检查任务归属，并清空 TaskInfo 持锁字段，防止旧任务误删新任务的锁。

## AGV 动态停车和出库

`LoadParkingLanes()` 从“agv停放点”识别物理巷道、深浅顺序及唯一入口。配置异常时输出原因并禁用相关停车安排。

回家时 `TryPark()` 按入口距离优先检查没有进出车辆的停车巷道，在该巷道选可进入的最深空位；外侧有车挡住的空洞不会被选中。使用 `ParkingLane.Owner` 占用巷道、`parkingTrips` 记录预留，先去入口再去停车位。`UpdateParkingTrips()` 确认停车完成后更新 `parkedAgvs`，释放 Owner。

派车使用 `CanLeaveParking()` 过滤正在回家、巷道忙或外侧有 AGV 遮挡的车辆，再选择合适的近车。出库由 `StartFromParking()` 占用巷道并进入 `GoParkingExit`；确认到入口后 `FinishParkingExit()` 解除占用和停车记录，恢复搬运目标与状态。

`parkingstaID` 仍用于初始化摆车；运行中回家不依赖固定 `homestaID`。停车区暂不可用时车辆保持当前位置等待，公共通道上的等待和拥堵仍依赖地图与宿主交管。

## 查询和当前测试入口

- `GetBatches()`：业务批次进度独立快照，最新在前。
- `GetBatchDetail(batchId)`：全部业务明细及执行阶段快照，不存在返回 null。查询不会派车或推进状态。
- 业务完成数以执行任务 `Finished` 为准，**包含回家停车**，不是仅卸货完成。
- `HttpApi.cs` 当前仅映射 `/api/agvs`、`/api/tasks`，监听 `http://localhost:8088`。业务批次查询函数尚未映射为 HTTP 路由。
- 当前初始化会清理、生成指定测试货物并按 `parkingstaID` 摆车。不能把重启脚本当作无副作用的恢复操作。
- `script.cs` 当前运行 `TestPocketMoveBatchCreation(new[] { "06", "07", "08", "09", "10" }, new[] { "01", "02", "03" })`，随后查询；还每 10 秒调用 `TestCargoBatchQueries()` 输出进度。切换测试时直接调整调用，保留代码中的 API 使用示例注释。
- `CargoInitializer.cs` 的 `GenerateCargo()` 选择站点的 `CargoAreas.First()` 放置托盘和货物，不按朝向分类选择区域。
- 并行执行上限当前为 4，调度周期 1000 ms。

## 已知边界与后续工作

- `CargoMoveType.AreaToArea`、`PointToPoint` 枚举不代表已有统一业务批次创建接口；当前巷道批次入口支持单巷道和多巷道列表。点到点清障另走 TaskCreator。
- 业务前提是只有本系统控制的 AGV 搬货。目前不要求货物唯一编号，不保存货物对象快照或比较对象引用；`CargoId` 字段预留但未赋值，不参与调度判断。查询返回独立的数据快照。
- 业务批次、执行任务、预留和停车占用都在内存；没有持久化重启恢复。后续恢复应结合任务阶段、AGV 载货和货位状态核对。
- 尚未提供完整的暂停、取消、NeedsReview 人工处理及恢复接口。
- 尚未实现多业务批次并行、双向搬运循环等待检测和完整公平调度。
- 停车位置记录依赖本脚本控制的初始化和进出流程，人工移车/外部指令后的自动对账尚未实现。
- 既往现场已反馈入口分段、搬运重叠、动态停车效果正常；不能视为所有异常和多车场景均已验证。

## 编译与验证

README 是文档，不加入 csproj 的 `Compile` 项；`project.config` 的 `CompileFilter` 加入 `*.md`，避免宿主将其作为待编译文本。

该项目依赖宿主 DLL 和 Windows/.NET 环境。可通过软件重新加载脚本编译；也可使用本机 Roslyn C# 编译器，引用宿主 DLL、.NET 6、ASP.NET Core 和 WindowsDesktop 程序集，对本目录全部 `.cs` 做库编译检查。单纯编译不会验证现场地图或车辆动作，也不要以运行 `Main()` 的方式做无副作用测试。

多巷道搬运还需现场验证：不同容量目标的顺序分配、在途预留占满后转向下一目标、某来源被占用时其他来源继续派发，以及总容量不足时整批拒绝。隔离验证不能替代现场地图和车辆联调。

修改调度后重点验证：前车卸货与后车取货重叠；卸货占用时在取货位等待；入口释放归属；容量不足不超派；外侧先出库、深处可达空位优先停车；批次异常暂停和完成统计。

现场需确认 `01`～`25` 分类及其站点配置，检查启动配置日志，验证不同朝向库位之间的取放货、目标区域中的货物显示朝向，以及朝向分类缺失或重复时保持等待的行为。地图配置缓存及朝向取放货尚未完成现场运行验证。
